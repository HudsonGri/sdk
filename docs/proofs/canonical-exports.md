# Canonical public export join

This is a source-reviewed integration contract, not a generated export inventory or proof. Exact source captures are in `evidence/source-review-20261026/sources.json`; no compiler output or rustdoc fixture was fabricated.

## Decisions

Use sdk-docs' existing `public_api::extract` through its public `build_data`/DocsData projection. `projection::build_family` retains effective exported occurrences, aliases, local implementation members, rendered signatures and compiler source spans. The standing guard must consume those canonical `families[].items[]` records rather than implement another Rust visibility/re-export walker. The lexical scanner remains a conservative source-drift fence.

Join each projected occurrence by package/Cargo target, exact profile, exported path, kind and signature. Rustdoc IDs and line numbers alone are unstable identities. One definition may have multiple exported occurrences; retain each alias and its effective source. Missing/generated/external spans require an explicit provenance join and cannot silently remove an occurrence. Source identity includes exact source-manifest and rustdoc receipt digests, generator/toolchain identity and the checked commit; an unrelated or historical docs bundle cannot admit a changed API.

The canonical `ProfileSpec::id` already binds package, target, defaults and features. `rustdoc_profiles::extract_owned_api` already supplies published owner, profile, signature-aware ProjectionKey, rustdoc package/version and docs-present signals. Its explicit Visibility::Public/local-item filtering is not a substitute for the full effective occurrence projection. Use the existing projection for occurrence enumeration and the existing Cargo/profile ownership metadata for availability. DocsData itself has no per-occurrence profile field; a producer must retain the existing profile execution identity alongside each exact projected bundle. Do not infer default/all-features coverage from the bundle label.

Every supported host, OS-gated, feature and WASM profile needs explicit status. Missing artifacts, zero selected exports, private rustdoc receipts, unsupported format, source mismatch and missing profile evidence refuse qualification. The existing sdk-docs checked format adapter owns compiler format conversion. Compare canonical exported-occurrence multisets with proof registrations; every new/changed signature requires its invariant and admitted receipt, even when a private definition's source is unchanged. Exact source registration alone does not prove an occurrence's complete mode contract.

The initial lane-artifact searches found no reusable bundle. A subsequent targeted search found retained real Windows sdk-generation CLI output under `D:/codex-sdk-docs-eb24-fe001/windows-lock-assertion-temp/`. [Capture provenance](evidence/canonical-exports-v1/capture.json) preserves26 actual artifacts/source inputs, including the original generation manifest, DocsData, availability, five raw compiler receipts and all six source inputs. All copied bytes match the original producer's artifact/source digests. This is a historical `demo` test workspace at eb54c87d3ba7138a36ce5e99768a7b04e2ad1834, not the current SDK or a qualified generator executable. No Rust build was started.

`scripts/proof_export_join.py::load_catalog` now consumes these canonical outputs. Callers must supply the exact manifest pin, checked revision/source digest, source root and complete required profile set. It checks retained raw artifact hashes, all source bytes, public format60 receipts and target/version identity, then joins the existing path/kind/signature occurrences to the existing executed-profile identities. The normalized rustdoc digest and ProfileId remain owned by sdk-docs; neither algorithm nor the export walker was duplicated. Every occurrence needs a source span and profile availability. Duplicate/orphan joins, missing profiles, zero selected exports and profiles with zero joined exports refuse. Generated/external source spans currently refuse pending their explicit provenance adapter.

[Observed candidates](evidence/canonical-exports-v1/occurrences.json) contain17 occurrences across five profiles, including both signatures of `demo::overloaded`. Every candidate is explicitly unqualified. These are input records for the future proof-registration join; the consumer alone does not admit a public API proof or enforce the standing guarantee. Current-source artifacts, alias/implicit-implementation fixtures, generated-source provenance, all OS/WASM profiles and integration with receipt-backed registrations remain open.

Thirteen tests exercise the actual retained output and explicit adversarial transformations. [Control admission](evidence/export-join-policy-20261026T035807Z/admission.json) distinguishes four semantic production-consumer controls (omitting source-byte, availability or profile-export closure, or dropping a feature signature) from two controls that still refuse but change the refusal reason. Only the four semantic controls count as invariant-acceptance controls. All selected runs are under1.4s; raw output and actual mutated implementations are retained. Generated RPC/schema, CLI/tool and TS/WASM export joins remain pending. The same proposed static workflow step now includes the consumer suite alongside the two earlier policy suites. This is branch wiring, with no observed hosted CI execution or full source/export qualification claim.
